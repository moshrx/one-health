# One Health Clinic Manager

Next.js App Router + TypeScript frontend, Supabase Auth/Postgres integration, and a responsive clinical workspace. All bundled patients and repertory values are fictional. This is a functional prototype, not a clinical production system.

## Start

Requires Node.js 20.9+ and npm.

```sh
npm install
npm run dev
```

Open http://localhost:3000. With no environment variables the app runs in browser-local demo mode. Use fictional data only; demo storage is unencrypted and shared by users of that browser profile.

## Supabase setup

1. Create a Supabase project in a region selected after your privacy review.
2. Execute `supabase/migrations/001_clinic_workspace.sql` in its SQL editor.
3. Copy `.env.example` to `.env.local`, set the project URL and publishable key, and restart Next.js. Never expose a service-role key.
4. Create a confirmed user in Supabase Authentication.
5. As a database administrator, provision a clinic, membership and workspace using the SQL below. Replace the user UUID with that user's Authentication ID.
6. Open Clinic Settings and sign in. An empty workspace is intentional; fictional local demo records are not silently uploaded.

```sql
with clinic as (
  insert into public.clinics(name,country)
  values ('One Health Demo','IN') returning id
), membership as (
  insert into public.clinic_members(clinic_id,user_id,role)
  select id,'REPLACE-WITH-AUTH-USER-UUID'::uuid,'owner' from clinic
)
insert into public.clinic_workspaces(clinic_id) select id from clinic;
```

RLS limits reads to members of the clinic and updates to owners/practitioners. Anonymous access and client membership changes are denied. Viewers cannot save. Audit metadata is generated by a database trigger, with no client write privileges. This migration is new and additive; it does not delete existing data. Membership management is deliberately administrator-only. Test these policies against a real Supabase instance before deployment.

Prototype persistence stores patients, encounters, prescriptions, follow-ups and bookmarks together in one clinic-owned JSON document. This is not the complete normalized schema from the brief. Writes replace the document, so concurrent edits can overwrite each other. Normalize into patient/consultation/prescription/etc. tables with clinic-scoped foreign keys, version checks and server-enforced lifecycle transitions before multi-user or real patient use. Supabase mode saves explicit records; browser demo mode additionally autosaves form drafts. Signing is a recorded review action in the UI, not a cryptographic signature or an immutable server-enforced clinical signature.

## Working prototype

- Dashboard, patient search, multi-category registration and category filter.
- Case-taking forms with category-specific fields, browser draft autosave, reviewed records and patient timeline.
- Seven bibliographic collection placeholders and remedy-name search/bookmarks. No source book text is included; attributions reflect the supplied brief and need bibliographic verification.
- Weighted synthetic repertory comparison with visible score explanation and record saving. Values are invented solely to demonstrate the interface, not medical knowledge.
- Practitioner-entered prescription fields, required-field/review gate, recorded approval and browser print-to-PDF from a saved prescription. No automated dose recommendations.
- Follow-up records and timeline, JSON export, Supabase sign-in and workspace sync.
- Responsive desktop/mobile layouts.

## Incomplete / launch blockers

- Authorised book imports, edition/page metadata, full text/symptom search, cross-references, reference notes, real repertory content and comparisons.
- Automated prescription safety checks, independently verified registrations, immutable signing, record amendment workflows and validation of clinical field values.
- Follow-up reminder scheduling, date-derived due status, comparative charts and dedicated single-prescription PDF templates. Dashboard due labels currently come from sample patient status.
- Patient attachments, secure object storage, consent enforcement, granular record access, patient-specific deletion/export workflows and normalized clinical tables.
- Appointments, billing, payment subscriptions, subscription plans, AI assistance and clinic administration UI. Navigation explicitly marks planned modules. No external AI service receives any patient data.
- Concurrency handling, session lifecycle UX, MFA, rate limiting, comprehensive audit trails, restore drills, monitoring, access reviews and tested disaster recovery.
- Region-specific India/UK date, currency and clinic settings; privacy/regulatory and clinical safety review in each target jurisdiction. The prototype makes no compliance claim.
- Hosted database integration and RLS isolation tests require a provisioned Supabase project; no credentials were supplied and no cloud resources were created.

Do not enter real patient information. This implementation has no diagnostic logic. Traditional reference content must be clearly separated from modern clinical evidence. Clinical improvement and deterioration must not automatically be attributed to treatment.

## Hosting and costs

Run on a Node-compatible Next.js host, with Supabase for Auth and Postgres. Configure HTTPS, environment variables, Auth URLs, appropriate regions and operational controls before launch. Commercial cost depends on hosting plan, database size, backups/PITR, bandwidth, storage and email volume. No paid services or subscriptions were purchased, and patient billing is not implemented. Check current prices at https://supabase.com/pricing and your chosen host before committing.

## Validation

```sh
npm run typecheck
npm run build
npx playwright install chromium
npm test
```

The end-to-end suite covers fictional registration, case saving/draft persistence, reference search, weighted comparison, prescription review gating, follow-up and mobile layout. These UI tests do not validate clinical effectiveness or production data security.
